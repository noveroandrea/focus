# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

Focus is a Chrome browser extension (packaged as **"Focus"**) that helps **anyone who struggles to stay focused** — whether from ADHD or ordinary distraction — keep on task during **study or work**. It injects an animated sprite companion into web pages that reacts to your activity: the character **bounces/steps while you work** and **cries (with an optional beep)** when you go idle.

The active character is rewarded for sustained focus — it starts at full size and gradually **shrinks** toward a minimum in proportion to accumulated focus "heartbeats" (≈one per active second), then bursts into **fireworks** and switches to a new character once it reaches the minimum size at `N` heartbeats (configurable 5–300, default 30). The new character restarts at full size with the count reset to 0.

The extension only activates on a **user-editable whitelist** of focus domains (writing editors, research/reference sites, docs, mail, etc. — anything the user considers "work"); every other page is left alone. An **optional AI classifier** (local by default, or a remote backend) can auto-whitelist unknown pages.

`desktop/` holds a small optional **agent for Windows, macOS and Linux** whose only job is to report which **program** is in the foreground. The extension polls it alongside `chrome.idle` and matches the answer against a **program whitelist** kept beside the domain whitelist, so work done outside the browser can be told apart from distraction outside the browser. The extension remains the central node — see "The Desktop Agent" below.

## Architecture

The extension uses a **message-passing architecture** where `background.ts` is the single source of truth for all state, but heartbeat *generation* lives in its own module:

```
User activity (mouse/keyboard/scroll)           OS-wide activity (any window / PDF viewer)
    ↓                                                ↓
heartbeat.ts (content script)                    chrome.idle poll (in heartbeats.ts)
  sends HEARTBEAT on real page activity            queried every 0.5s
    └───────────────┬───────────────────────────────┘
                    ↓
heartbeats.ts — the two heartbeat sources + accumulation + the idle countdown anchor
    ↓ (via a small host interface: getState/getSettings/updateState/touchState/isAllowedUrl)
background.ts (service worker) — owns SessionState, persists to chrome.storage.local
  • broadcasts STATE_UPDATE to all tabs + popup on any change
                    ↓
sprite.ts (injected UI) + popup/Popup.tsx + pip.ts (floating companion) — pure renderers of the received state
```

### Activity & counting model (important)

State is driven by **heartbeats**, generated entirely in `src/extension/heartbeats.ts` (not `background.ts` — that file only owns the state and reacts to it). There are exactly two heartbeat sources:

1. **Page activity** — `heartbeat.ts` sends a `HEARTBEAT` message on mouse/keyboard/scroll on an authorized page.
2. **OS activity** — a `chrome.idle.queryState(15)` poll (every **0.5s**) covers PDFs, plugin viewers, and other windows where no content script runs. Always queried at the **15s floor** (Chrome's minimum), never at the user's `idleTime` — querying at `idleTime` gives a binary flip with no visible countdown, because "active" refreshes `lastHeartbeat` to now right up until the instant it isn't. The first "idle" reading anchors the last input at `now − 15s` and the readout counts down a fixed `OS_IDLE_COUNTDOWN_S` (5s) from there, regardless of `idleTime`.

**Counting is event-driven, NOT timer-driven.** `registerHeartbeat()` (in `heartbeats.ts`) is called from every heartbeat source. It advances `heartbeatCount` by one, **throttled to ≈once per real second**. This matters because an MV3 service worker is suspended between events and its `setInterval` timers don't fire reliably while asleep — but an incoming heartbeat always wakes the worker and lands in `registerHeartbeat`. When the count hits `iconChangeHeartbeats` it advances `currentIconId`, resets the count to 0, and bumps `iconChangeAt`.

**One step per heartbeat.** `sprite.ts` moves one step on every change of `heartbeatCount`, so the sprite steps exactly once per heartbeat regardless of source (page interaction OR idle poll). There is no separate per-DOM-event movement path.

**PDF/plugin viewer tabs are a special case.** Chrome serves a PDF as an HTML wrapper around `<embed type="application/pdf">`, so `heartbeat.ts` technically runs there — but real input goes to the viewer's inner frame, which the wrapper can never observe. `heartbeat.ts` therefore detects this (`document.contentType !== 'text/html'` or an `embed[type="application/pdf"]`) and **stays completely silent** rather than pinging: pinging would register the tab as an observable HTML page and make the background wait forever for HEARTBEATs that can never arrive. A silent tab is picked up correctly by the OS idle poll instead, exactly like any other viewer.

**`osHeld` (violet countdown).** When the OS poll sees input but no page heartbeat arrived recently (`PAGE_INPUT_FRESH_MS`), the work is happening somewhere the page can't see — another app, or inside a PDF viewer — and `SessionState.osHeld` is set so the sprite's "I ⋯s" countdown renders violet instead of blue. Same countdown either way; only the colour differs.

> **Platform gotcha (do not re-litigate):** if `chrome.idle.queryState` reports `"active"` forever and the idle countdown never falls, **check how the browser is launched before touching this code.** Running Chromium/Brave with `--ozone-platform=x11` on a Wayland session routes it through Xwayland, whose XScreenSaver idle counter never advances (the Wayland compositor handles input) — `chrome.idle` will report `"active"` permanently no matter what the extension does. This is a browser-launch problem, not an extension bug; an earlier version of this codebase built a large amount of `idleApiProven`-style workaround machinery around this exact symptom, all of which was later deleted once the real cause (a stray `--ozone-platform=x11` flag in a `.desktop` file, left over from a picture-in-picture experiment) was found and removed.

### Key Files

- **`src/types.ts`** — Shared types: `SessionState`, `Settings`, `MessageType`, `CryBeepStyle`, `SpriteMode`, `IdleReaction`. Exports `CHARACTER_COUNT` (15), `DEFAULT_SETTINGS`, `round2`, and clamps: `clampIconChangeHeartbeats` (5–300), `clampIdleTime` (15–300, default 20; 15 is Chrome's idle floor), `clampCryBeepVolume/Duration/Style`, `clampSpriteMode`, `clampIdleReaction`.
- **`src/extension/agent.ts`** — the optional desktop agent's client side: polls `http://127.0.0.1:47317/` for the foreground program, plus the browser list, the exact-match whitelist test, and the learned identifier → name labels. Fails soft — with no agent installed it returns null forever and every caller falls back to the browser-only behaviour.
- **`src/extension/push.ts`** — **Web Push, sent by this browser straight to the user's phone.** The VAPID keypair is generated *per install* (WebCrypto ECDSA P-256, kept in `chrome.storage.local`) rather than held centrally, and that is the whole design: a shared key cannot ship in a public repo, holding it on a server would route every idle event through that server, and the timing of those events is the most sensitive thing here. So there is **no Edge Function and no send path through Supabase** — the worker signs a VAPID JWT, encrypts the payload with RFC 8291 `aes128gcm` (keyed by the device's own `p256dh`/`auth`, so FCM and Apple relay bytes they cannot read) and POSTs the endpoint. `Urgency: high` pierces Android Doze, and the **default `TTL: 0`** means a nudge that cannot be delivered *now* is dropped rather than queued — a warning arriving 40 s late is worse than none, because the countdown is over and the penalty has landed. The TTL is a **parameter** because a test has the opposite deadline: pairing confirmations and *Send test buzz* pass `TEST_PUSH_TTL_S` (5 min), since **iOS shows no notification while the web app it belongs to is the app on screen** — the user has to leave it, and a dropped test proves nothing. **Only 404/410 (subscription gone) prune the device**; 401/403 are a rejection of the *sender*, fail identically for every phone, and are logged with the service's own reason rather than deleting anything — pruning on them once destroyed a good pairing over a `sub` claim Apple would not parse. The VAPID `sub` comes from `PUSH_LANDING_URL` because **Apple validates it and FCM does not**: `mailto:…@localhost` is a 403 on every push to an iPhone and silently fine on Android. Nothing is ever retried. Verified end-to-end by decrypting a real `sendPush` body as the receiving device would — see BUGS.md.
- **`src/extension/heartbeats.ts`** — **All heartbeat generation**, isolated from state ownership. Both sources (page `HEARTBEAT`, the `chrome.idle` poll — now qualified by the agent's foreground program, see the Desktop Agent section), the throttled accumulation (`registerHeartbeat`), the OS-idle countdown anchor, and the viewer-tab bookkeeping (`contentTabs`) live here. Talks to `background.ts` only through a small `HeartbeatHost` interface (`getState`/`getSettings`/`updateState`/`touchState`/`isAllowedUrl`) — `background.ts` remains the only writer of `SessionState`.
- **`src/extension/background.ts`** — Service worker. Owns `SessionState`, wires up `heartbeats.ts` via `initHeartbeats()`, runs the 1s status loop (day rollover, `forceActive` tick, backup idle expiry, idle-penalty scoring), the AI classify proxy, the PDF/viewer classification flow, and draws the toolbar icon (green "Working" / grey "forceActive") with OffscreenCanvas.
  **An idle lapse costs three rising amounts, not one flat charge** — `penaltyStages()` in `timings.ts`: **−5** at warning+grace (10 s), **−10** thirty seconds later, **−15** at the moment the auto-pause fires. Rising, because one number says the same thing whether you looked away for eleven seconds or eleven minutes; and the first is the *smallest* because at ten seconds you have glanced out of the window, not abandoned the day. The last stage is **pinned to the auto-pause** rather than given a time of its own, which keeps `cryBeepDuration` the single answer to "how long does a lapse go on for" — and is why the earlier stages are **filtered**, not merely listed: that slider goes down to 10 s, where the lapse ends at 15 s and a −10 scheduled for 40 s would be a countdown to something that can never happen. `trackIdlePenalty` walks the schedule in a **loop**, summing everything due into one write, because a worker that was suspended can wake with two stages owed and paying them a second apart would charge for the wrong seconds — and two `penaltyAt` nonces set in the same millisecond would show one fly-up out of two. The countdown to the next stage is **broadcast** (`nextPenaltyAt`/`nextPenaltyAmount`) rather than recomputed per surface: the sprite, the companion canvas and the phone nudge all read the same two numbers, so none can disagree with the scoring, and a content script never needs to know `cryBeepDuration`.
  **`saveSettings()` is the only background-side writer of `Settings`, and it is not a convenience.** The `chrome.storage.onChanged` listener that mirrors whitelist edits to the server diffs the incoming value against the in-memory `settings`; that works for the **popup**, which writes storage directly, but a write made *here* updates `settings` first, so the listener sees no change and `queueDomains()` never runs. The edit was then deleted by the next server reply, since `applyState()` overwrites `allowedDomains` with whatever the server sent. `saveSettings()` does the follow-ups itself. See BUGS.md, "A page whitelisted from the companion un-whitelisted itself seconds later" — do not move them back into the listener.
  **`OPEN_COMPANION` owns companion windows**, one per screen. It tracks every open window id (`pipWindowIds`, pruned by `chrome.windows.get` on read rather than by `windows.onRemoved`, which a suspended worker is not around to hear) and places each new one bottom-right of the first display that has none, via `chrome.system.display`. The size is **231×200** — 23% off each side of the original 300×260, so a little under 60% of the area, having taken 10% back when the window became translucent (fading the whole window spends some of the contrast the smaller size was relying on) — which the content survives because the drawing is a 480×240 picture scaled into whatever box it gets and the whitelist bars ellipsize; the only part that does not shrink is the frame the platform draws, so the height loses proportionally more of its content than the width. **The count is not a setting and must not become one**: how many companions you want is a fact about the desk rather than a preference, the browser already knows it, and a number the user has to keep in step with the monitors they plug in is a number that will be wrong. The Working button opens one per display; the ⧉ button on a companion asks for one *more*. It lives here and not in the popup because the popup closes the instant the new window takes focus, losing the callback that was supposed to record its id.
  **Placement works on Windows, macOS and X11 — and is ignored on Wayland**, where xdg-shell has no request for a client to position its own toplevel. The `left`/`top` are still computed correctly there (`chrome.system.display` reports every monitor on Wayland, and the *size* is applied, because a client does choose its own buffer size); they are simply discarded by the compositor. The GNOME bridge therefore places the window itself, from inside the compositor — see `desktop/gnome-extension/`. This is the same wall as pinning and has the same one answer.
  **The phone nudge (`buzzPhone`) is hooked into `writeState`, on the active→idle edge** — the same transition every surface starts its countdown on, and the single funnel every state writer goes through, so a future path into idle cannot forget it. Three guards, each load-bearing: `forceActive` (paused earns nothing, so it nags about nothing); a **real lapse** test, `now - lastHeartbeat >= idleTime` — the flag is also cleared by things that are not lapses, notably `REMOVE_DOMAIN` mid-click, and a phone that buzzes for a button you just pressed is one you learn to ignore; and `NUDGE_COOLDOWN_MS` (5 min), **persisted** under `focusNudgeAt` because a cooldown in a module variable resets exactly when the worker has been suspended, which is exactly when the user was away.
  **One nudge is not enough, so the lapse keeps asking.** After the first, `repeatNudge()` fires every `NUDGE_REPEAT_MS` (5 s) from the one-second status loop — no timer of its own, since that would be a second thing to keep alive in a worker that suspends. The text is a countdown to what it will cost (`nudgeText`), because "come back now and it costs nothing" and "you are already paying" are different messages; once every stage has landed there is no number left to offer and it is a bare `FOCUS!`. The schedule advances from itself rather than from the send, so a 1 s tick cannot let jitter accumulate. **It has no stopping rule of its own** — it ends when the session stops nagging (you return, or the auto-pause to *Not working* fires), so `cryBeepDuration` remains the single "how long does Focus nag me" knob and there is no second number to keep in step. `nudgeRepeatAt` is deliberately **not** persisted, the opposite of the cooldown: a revived worker resuming a rhythm it never saw start would open with a burst for a lapse that may be over. The text is written **`PUSH_LATENCY_MS` (4 s) ahead of now**, because a push takes a few seconds to reach a phone and the countdown it carries is stale on arrival by exactly that much — "15 seconds before −10" landed on a screen where the truth was 12. Four rather than the measured three so the error falls on the side of under-promising; the on-screen countdowns are untouched, since nothing is in flight to compensate for. The burst ends with the one push that **reports rather than warns** — *"⏸️ Not working"*, sent from the auto-pause branch itself because `buzzPhone`/`repeatNudge` both refuse while `forceActive`, which is what the next line turns on — and only if this lapse was actually nudging, so a burst the cooldown suppressed stays silent all the way through instead of announcing a status change out of nowhere. It carries `PAUSE_PUSH_TTL_S` (60 s): a statement of fact stays true in a queue, unlike a countdown, but not after the user has come back and pressed Working. `penaltyStages()` is the single description of the penalty timeline, so the phone's countdown and the scoring cannot describe different futures. The sending is `push.ts`'s and goes to no server, so there is nothing here to rate-limit but the phone's patience.
  **Pairing is six messages and the background owns all of it** (`PUSH_PAIR_START` / `PUSH_PAIR_POLL` / `PUSH_PAIR_RESUME` / `PUSH_PAIR_CANCEL` / `PUSH_LIST` / `PUSH_FORGET`, plus `PUSH_TEST`), because the keypair and the paired devices live here and a popup that closes mid-flow must not be able to lose either. **On iPhone that popup is guaranteed to close** — the flow is minutes of tapping on a different device, and a Chrome popup dies the instant the browser loses focus — so the outstanding nonce is persisted (`focusPairPending`) and polled from a `chrome.alarms` job (`focus-pair-poll`, the usual reason: a suspended worker's timers do not fire), completing and sending the confirmation push with nobody watching. `PUSH_PAIR_RESUME` is what a reopened popup asks so it rejoins that QR instead of pressing the button again — which would call `create_pairing`, and that **deletes the caller's outstanding rows**, destroying the pairing the phone is on its way to claim. `PUSH_PAIR_START` puts **two** things in the QR and only two: a one-use nonce and this install's VAPID public key — the key has to travel because a subscription is *bound* to the sender's key, and one minted against anybody else's would refuse every push this browser sent.
  **`programIsDriving()` decides which whitelist is earning right now**, and the page's answer is its *complement* rather than its own test. `osHeld` is the obvious signal and the wrong one to read directly: it goes true after only `PAGE_INPUT_FRESH_MS` (2s) of sitting still on a page that is still being counted, and it is also set while reading a PDF, where the browser genuinely is the work but no page heartbeat can ever arrive — `!osHeld` would call both idle. Exactly one side can be driving, so "no allowed program is holding this session up" is the page's answer, and with no agent installed it degrades to what was always true.
  **Both answers are gated on `heartbeatsLanding()`, not on `isHeartbeatActive`.** That flag covers the whole idle timeout *including* the final stretch where `chrome.idle` has already reported idle, the anchor is set and the "I" countdown is falling — a stretch in which no heartbeat is registered and no point is earned, so WORKING there would describe a session that has already stopped counting, beside a number counting down to zero. `heartbeatsLanding()` adds "and `lastHeartbeat` is fresher than `WORKING_FRESH_MS`", which flips exactly when the background pins `lastHeartbeat` back to the anchor — itself a broadcast, so the companion's bars turn over on it instead of up to 2s later on their poll.
- **`src/extension/content/heartbeat.ts`** — Content script that detects activity on authorized domains and sends `HEARTBEAT` / `FOCUS_PING` / `CLASSIFY_PAGE`. Domain defaults: Overleaf, arXiv, Nature, IEEE, Claude AI, Google Scholar, Wikipedia, UNIPD, mail (Gmail/Outlook) — all editable. **Detects and stays silent on PDF/plugin-viewer documents** (see below) rather than pinging from a wrapper that can't see input.
- **`src/extension/content/sprite.ts`** — Vanilla-TS sprite injected into all pages. Renders the 15 characters, shrinks as `heartbeatCount` rises, cries + beeps when idle (beep styles: **`ramp`** rising volume, **`pulse`** steady beeps every 5s, **`siren`**), plays fireworks on `iconChangeAt` change, and is draggable. Uses inline styles (not Tailwind) to survive host-page CSS. Audio uses the Web Audio API with **capture-phase** unlock listeners (`pointerdown`/`keydown`/`touchstart`/`click`) so it works even on SPAs that `stopPropagation` input events. Shows an "I ⋯s" / "W ⋯s" phase countdown (violet when `osHeld`).
  **`Settings.spriteEnabled` is a kill switch, not a pause.** Off, nothing is drawn into any page — which takes an explicit guard in `triggerIconChange()` and `triggerPenalty()` as well as the hidden wrapper, because the fireworks live in `#focus-flow-root` and the penalty label is drawn at the screen centre, so neither is inside the element the switch hides (see BUGS.md) — for people who watch a companion window on another screen instead. Everything else is untouched, because heartbeats, scoring and the whitelist belong to `background.ts` and never to this file; the idle **beep** also stays, since it is part of the idle escalation rather than part of the drawing, and someone who stopped the sprite walking over their page has not asked to stop being told they went idle.
  **Three shapes, one setting** (`Settings.spriteMode`): `roam` (the walking circle, one step per heartbeat — the default and the original), `fixed` (the same circle parked where you dragged it, spending each heartbeat on a hop instead of a step), and `panel` (the whole companion inside the page — `../ui/companion` in a draggable box, whitelist bars included). `panel` exists because the companion *window* has one hard requirement the page does not: something outside the browser must keep it on top, and on macOS and most Wayland desktops nothing will. Inside the page the browser is the compositor and the problem disappears; the cost is that it is only visible while you are looking at the browser.
  **The wrapper element is load-bearing.** The circle's position lives on an outer `wrapEl` and its scale on the inner `spriteEl`, because `transform` holds one value: the `transform 0.9s linear` easing that makes the shrink pleasant would also smear a 300 ms hop and a per-frame shiver into nothing. Position + per-frame motion on the wrapper, size on the circle.
  **The idle escalation is two things, only one of which is a setting.** The **tremble** is always on and has none: it starts at the **start of the warning window**, not at the escalation after it, so it is visible while there is still time to come back, and it ramps for as long as the lapse runs. Offering to switch it off would have meant offering to switch off the one thing that is *meant* to catch your eye. **`Settings.idleGrow`** covers the other half — swelling to fill the frame — which is the part that takes over the screen and therefore the part worth being able to refuse. One setting, every surface: the two circle modes grow into the page, and the panel and the companion window grow *inside their own frame* (a fixed-size box does not stop the drawing in it from swelling, which is why the panel is not exempt).
  **The tremble escalates in DISTANCE, never in rate.** A new direction is chosen on a fixed clock (`TREMBLE_STEP_MS`, ~18 Hz) and held until the next one; what the lapse buys is how far it jumps — from `TREMBLE_MIN_PX` (10) at the start of the warning to `TREMBLE_MAX_PX` (96 CSS px ≈ 2.5 cm) after `TREMBLE_RAMP_MS` (25 s). Those read completely differently: a rising rate becomes a buzz and smears, while a rising distance stays a series of steps you can count. The floor is not decoration — a ramp starting at zero is invisible through exactly the seconds the warning exists for.
  `trembleAmplitude()` is shared between the circle and the canvas so the two curves cannot drift, but each **clamps it to the room it has**: the sprite to the viewport margin on each side (a companion parked in a corner must not shake itself off-screen at the moment it is trying hardest to be seen), the canvas to `DISC_X - DISC_R` / `DISC_Y - DISC_R`, which is literally the gap between the character and its frame. The canvas also converts through its own **rendered** size (`unitsPerCssPx()`), so the shake is the same physical distance whether the window is a corner thumbnail or dragged out large. It therefore tops out well short of the in-page sprite — a page is as big as the screen, the drawing is 480×240 and the character is a third of it. Clipping a character against a hard rectangular edge does not read as a violent shake; it reads as a bug.
  Drag positions are kept in `chrome.storage.local` under `focusSpritePos` as **fractions** of the viewport (per mode), not in `Settings`: a drag is not a preference, and routing one through the settings object would fire the whole settings-changed cascade (whitelist diff, server mirror, icon repaint) on every drop.
- **`src/extension/ui/companion.ts`** — **the companion panel itself**, and the one implementation behind both of its homes: the floating window (`pip/pip.ts`) and the sprite's `panel` mode inside a page. Exports the character roster (`CHARS`/`CRYING` — sprite.ts reads them from here too), `createCompanionCanvas()` and `createWhitelistBars()`.
  The canvas is a fixed 480×240 drawing that scales into whatever box its host gives it, animated on `requestAnimationFrame` (which the browser stops calling while the window is hidden — most of this panel's life). Everything it animates is driven by the **timestamp nonces** `iconChangeAt` / `penaltyAt`, never by the scores changing, for the same reason sprite.ts does it that way: the server reconciles the displayed score after every post, so a changed score is not evidence anything happened here. Fireworks + a `+N` fly-up on a character change (the amount read from the actual `focusScore` delta, so "Not working" — which earns nothing — shows no number), a `−N` fly-up on each penalty stage (the amount from `penaltyAmount`, since a lapse charges −5, then −10, then −15), a heartbeat bob, and the idle escalation: a tremble ramping from the moment the session goes idle (always), plus a grow starting when the warning ends if `Settings.idleGrow` is on (`MAX_DISC_SCALE` is *derived* — the distance from the disc's centre to the farthest corner — not a guessed constant).
  **Draw order is the contract.** The character is drawn first and the score, the countdown and their plates after it, so a character grown big enough to fill the frame covers the background and never the numbers. The plates only appear once the disc has actually grown (`grow > 1.05`): grey text on a flat grey fill is unreadable and a shadow alone does not save it. The two whitelist bars are DOM rows *under* the canvas, so they are out of the drawing's reach entirely.
  **It must have no runtime imports.** `sprite.ts` is a content script, injected as a classic script, so `vite.config.ts` inlines its dependencies back into the bundle — and that inliner refuses a dependency which itself has imports. `IDLE_WARNING_MS` is therefore passed in by both callers rather than imported. Adding a real import here breaks the build loudly, but it does break it.
  The **two whitelist bars** live here as well: the front tab's domain (`WHITELIST_PAGE` / `UNWHITELIST_PAGE`) and the foreground program (`ADD_PROGRAM` / `REMOVE_PROGRAM`), each a "+ Whitelist" button when it is off the list and, when it is on, a **✓ WORKING / IDLE** status plus a quiet ✕ — or a red *"Focus agent is off"* line when the agent is not running. The status word is the live one (`PageStatus.working` / `AgentStatus.recentWorking`, both from `programIsDriving()`), not "whitelisted", because those are two different facts and only one of them changes minute to minute: with a companion on each screen, moving from the editor to a whitelisted page shows the program going quiet and the page lighting up. It is refreshed from the 2s poll *and* from `noteState()` on any `osHeld`/`isHeartbeatActive` broadcast, since that switch is something the user does deliberately and watches for — but only on those two flags, because refreshing on every `STATE_UPDATE` would be two messages a second while working. It polls `PAGE_STATUS` and `AGENT_STATUS` every 2s while the document is visible. Both bars are built by one `makeBar()` so they cannot drift apart. `UNWHITELIST_PAGE` drops **every** entry matching the URL (`matchingDomains()`, the same substring test as `isAllowedUrl`), because removing only the exact hostname would leave a broader entry still counting the page and the tick still showing — a button that visibly does nothing. `PageStatus.matched` carries those entries so the ✕'s tooltip can name what it will actually drop. They exist here as well as in the popup because this panel is *always visible*: the popup is several clicks away and covers the page it describes. The red state waits 4s (`OFF_GRACE_MS`) before appearing: a woken service worker answers the first `AGENT_STATUS` from an empty cache, since its poll timer did not survive suspension, so "not running" is a normal *first* answer from a machine whose agent is fine. It renders `AgentStatus.recent` (the last **non-browser** program), never `.program`: the companion window *is* the browser, so the live reading while you look at it is always a browser — the one answer the program whitelist must refuse. Same reason the popup's panel uses `recent`; the popup is browser chrome too. **`PageStatus` is the same problem for pages**: that window is itself a window, so "which tab is active?" answers "the companion" exactly while you look at it — `background.ts` therefore remembers the last `http(s)` tab (in `updateActionIcon`, which already runs on every event that changes what is in front) and answers from that. `WHITELIST_PAGE` deliberately ignores `NEVER_WHITELIST`, which exists to stop the *classifier* auto-adding YouTube; the popup's own per-page toggle honours a deliberate click too, and the two surfaces must not disagree about the same page.
- **`src/extension/pip/pip.ts`** — The **floating companion window**: a small standalone `chrome-extension://` window (`pip.html`) meant to float above other apps while you work outside the browser. Almost nothing is drawn here — `../ui/companion` is; what is left is what only a *window* has. Not video picture-in-picture (removed — see the README's "Floating companion" section for why). Opened from the popup's Working button only when *resuming* work, gated on `Settings.companionEnabled`.
  **The pin line** is three answers, not one message, chosen from `navigator.userAgentData.platform`: on **Windows** and **Linux** something outside the browser does the pinning automatically, so it is a "Pinning on top…" progress line that gets out of the way after `PIN_WAIT_MS`; on **macOS** nobody can, so it prints what the user has to do by hand and does not fade. Two agent answers are definite enough to overrule it — a stopped agent on Windows (nothing is pinning) and `AgentStatus.note` on Linux (an agent that cannot see the foreground is an agent with no GNOME bridge beside it, and the bridge is what pins there). Silence proves nothing. One click dismisses the line for that window.
  The **⧉ button** opens *another* companion. Placement is the background's (`OPEN_COMPANION`, below), not this window's.
  **The Working / Not-working toggle is here because the popup is behind whatever covers the browser.** It writes `Settings.forceActive` to storage and *nothing else* — every consequence (snapping the session active, `resetOsAnchor()`, clearing the lapse bookkeeping, the toolbar repaint, the server check-in) belongs to the `storage.onChanged` listener in `background.ts` and must go through it identically however the flag was flipped. It **re-reads** settings inside the click rather than spreading the copy this window has been holding: a companion is open for hours while the popup edits the whitelist and the classifier underneath it, and a stale spread would silently undo those. It deliberately does *not* copy the popup's whole behaviour — resuming there also opens one companion per display, which from inside a companion is a button that duplicates itself.
  **The favicon is the character disc in miniature** (`paintFavicon`), because a window that is minimised or half-covered is reduced to a title and an icon, and that icon may as well answer the question the window exists for: `char.color` while counting, grey + `CRYING[0]` when idle, `filter: grayscale(1)` while paused — the same three inputs, and the same greying, the canvas uses, so the taskbar and the window cannot disagree. Redrawn only when that triple changes: `STATE_UPDATE` arrives about once a second while working, and each repaint is a canvas encode plus a `<link>` swap. The crying frame is fixed rather than the canvas's 450 ms cycle — an animated favicon is a new data URL twice a second for a picture 16 px across. A *window* has a title-bar icon and the in-page `panel` does not, which is why this lives here rather than in `ui/companion.ts`.
- **`src/extension/ui/shared.tsx`** — **everything the popup and the dashboard both render**: the charts, the leaderboards, the member profile, the team/friends/competition sections, the whitelist editor, and the hooks that fetch them. Two surfaces, one implementation — which is what keeps the *data* rules single-sourced (60-second board refresh, fetch-once day series, profiles only on click). Layout lives in each surface; nothing else does. It must never import either surface: both call `createRoot` at their top level.
- **`src/extension/ui/wide.tsx`** — the chart forms that need room, so they stay out of the popup bundle: a composition donut, a calendar heatmap, a weekday profile, a stat tile. Each is a second *reading* of a response another component on the same screen already fetched — never a new request.
- **`src/extension/popup/Popup.tsx`** — 320px popup: activity status, per-page whitelist toggle, section pills, and Settings (idle time, icon-change heartbeats, beep volume/duration/style, **sprite mode + idle reaction**, AI classifier fields, allowed-domain editor, floating-companion toggle + always-on-top help). The idle-reaction control is hidden rather than disabled in `panel` mode: a control that cannot do anything is worse than no control. The header's expand button opens the dashboard in a tab.
- **`src/extension/dashboard/Dashboard.tsx`** — the same data in a full tab: sidebar of scopes, KPI row, panels side by side. A *second view, not a second client* — every request goes through the background, so it inherits the Supabase session and every RLS policy untouched. (A hosted page would need its own session and its own OAuth redirect, against a schema where `get_member_profile` hands out other people's browsing data.)
- **`src/components/SpriteSimulation.tsx`** — Standalone demo used by `index.html` (`npm run dev`) to develop the sprite without Chrome APIs (shortened interval).

### AI auto-classify (configurable backend)

On `CLASSIFY_PAGE` (HTML pages) or the background viewer flow (PDFs), `classifyPage()` in `background.ts` calls an **Ollama-compatible** HTTP API and expects a `YES`/`NO` answer:

- **`classifyUrl`** — backend address. Local: `http://localhost:11434`. Remote: the server's base URL.
- **`classifyApiKey`** — sent as `Authorization: Bearer …`; leave empty for a local model.
- **`classifyModel`** — model name. **Required** — the address says *where*, the model says *which*; Ollama's `/api/chat` needs a `model` field.
- **`classifyNumThreads`** — `num_thread` cap so a request can't pin the CPU.

The code speaks Ollama's request/response shape (`/api/generate` warm-up + `/api/chat`, reads `data.message.content`). To target **Gemini / OpenAI / Claude**, edit `classifyPage()` — the README has ready-to-paste examples. If the backend is unreachable it returns `{ isStudy: false, offline: true }` and the page is simply left inactive, so the extension always works without any AI.

### Optional Supabase sync (`withserver` branch)

Off by default and **completely inert** until `src/extension/server/config.ts` is filled in *and* the user signs in — every call short-circuits on `isServerConfigured()`, so the extension still works with no backend.

- **`src/extension/server/auth.ts`** — Google sign-in via `chrome.identity.launchWebAuthFlow` (**not** `getAuthToken`, which is Chrome-only and absent in Brave), exchanging Google's `id_token` for a Supabase session. Refreshes are collapsed into one in-flight promise because Supabase rotates the refresh token on use — two parallel refreshes would sign the user out.
- **`src/extension/server/sync.ts`** — sends score **deltas** (`+focus` / `−distracted`), never absolutes, so two devices on one account can both post without overwriting each other. Pending deltas live in `chrome.storage.local` (an MV3 worker is suspended constantly) and clear only on server confirmation. The client posts at four moments — a score change, the browser opening, the Working button, and a **1-minute floor** — and **knows nothing about rollover**: it renders whatever live score comes back, so just after a server rollover it may briefly show the old figure until its next post.

The floor is a `chrome.alarms` one-shot (`focus-sync-post`) re-armed by every post, so it measures *time since last contact* rather than free-running. It exists because the other three triggers are all things the **user** does: a session with no score changes — reading a PDF, another device doing the earning, or simply idle — would otherwise sit indefinitely on a stale live score, stale averages, and a day the server has already ended. It must be `chrome.alarms` and not `setTimeout` for the same reason heartbeat counting is event-driven (a suspended worker's timers don't fire), and 1 minute is the shortest useful period because Chrome clamps alarms below that. Signing out clears it; signing in re-arms it, since signing in posts.
- **`web/`** — **the pairing web app**, the one page a phone ever opens. Hosted HTTPS and not a page inside the extension, because push needs a service worker and a service worker needs HTTPS: a `chrome-extension://` URL means nothing on a phone. It asks Android-or-iPhone (the extension asks first too, and for the same reason: the flows genuinely differ — Android subscribes from a plain tab in two taps, iOS refuses until the page is added to the Home Screen and opened from there, which is four taps through a menu most people have never used), subscribes with the extension's VAPID public key, and hands the subscription back through `claim_pairing`. **Getting the pairing code from the Safari tab into the installed app is the hard part, and only one carrier is guaranteed.** It travels in the query string — and `manifest.webmanifest` therefore declares **no `start_url`**, which is load-bearing and not an omission: a manifest that names one launches the installed app *there* rather than at the URL that was on screen, so `?p=…` was dropped and the Home Screen icon opened asking the user to scan the QR they had just scanned. Absent, the spec defaults it to the document URL. `localStorage` is mirrored too but **cannot** help on iOS, where a Home Screen web app has its own storage partition — the original "one of the two will survive" was two carriers riding the same boundary. The one that always crosses is the **system clipboard**, carrying the *whole link* rather than the bare code — it is what is already in the address bar, so a long-press on Safari's own URL works as well as the button, which matters on a platform that refuses clipboard access often enough that a button relying on the async API alone appears to do nothing. Three paths, most-refusable first: `navigator.clipboard`, then selection + `execCommand` with `readonly` lifted (iOS will not select a readonly field), then the always-visible field the user can copy by hand. Deploy anywhere static — `web/README.md` covers GitHub Pages and a Supabase Storage bucket — and set `PUSH_LANDING_URL`; empty makes the popup say pairing is unavailable rather than show a QR that leads nowhere.
- **`supabase/migrations/`** — three score tables (`daily_scores`, `user_domains`, `user_summary`), four team tables (`teams`, `competitions`, `team_members`, `team_competitions`), one write RPC (`apply_score_delta`) and its read-only twin (`get_state`), and the rollover. Every RPC returns the **full state**: `{ summary, domains, days, teams, competitions }`.

**Teams and competitions.** `team_members` is keyed `(user_id, team)` and `team_competitions` `(team, competition)` — the composite primary keys *are* the duplicate prevention, with no application check to forget.

**A competition has two kinds of entrant, and one person can be both**: `competition_members` (you, ranked against other individuals) and `team_competitions` (your team, summed, ranked against teams). They are separate opt-ins — being in a team that entered a competition does not enter *you* — which is why the popup shows the same competition twice, once per entry (`comp:<name>` vs `comp:<name>:<team>`). **At most one of your teams may be in any one competition.** That rule spans `team_members` and `team_competitions`, so no table constraint can express it; it is enforced at *both* doors — `enroll_team` (checking **every** member of the team, since whoever presses the button is rarely the person the clash belongs to) and `join_team` (joining a team already entered where you field another). Guarding only one leaves the other as a way in. `teams`/`competitions` are thin registries so foreign keys work and so "create" (refuses an existing name) and "join" (refuses a missing one) can be different operations. Membership writes are `join_team` / `leave_team` / `enroll_team` / `leave_competition`. **Teams and competitions both carry a bcrypt password** (create sets it, join must match), held in a `password_hash` column withheld from clients by column-level `GRANT SELECT (name, created_by, created_at)` — RLS filters rows and cannot hide a column. `join_team` and `enroll_team` are therefore SECURITY DEFINER (they read that column); the others are SECURITY INVOKER under RLS. Because DEFINER bypasses RLS, the explicit `user_id = auth.uid()` and team-membership predicates inside those two are load-bearing, not redundant. The competition password exists because without it anyone could create a throwaway team and enrol it into a known competition name, which legitimately made every rival team visible to them. `leave_competition` is deliberately not passworded.

**`visible_teams()` is the single definition of who a participant may see**: their own teams, plus every team sharing a competition with one of theirs. Both consumers go through it — `build_teams()` (which displays) and `get_member_profile()` (which authorizes) — so the two can never drift into disagreeing. `build_teams()` is SECURITY DEFINER built to the safe shape: **no arguments**, caller from `auth.uid()`, `EXECUTE` revoked from `anon`/`PUBLIC`.

**`can_see_user(p_user)` is the single definition of whether one participant may see another**: yourself, anyone in a team reachable through `visible_teams()`, or an **accepted** friend. A *pending* friend request grants nothing — asking to see someone is not permission to. Everything that exposes one user to another goes through it.

**Friends** (`friendships`, keyed `(requester, addressee)` with a status) are a second route to visibility alongside teams, needing both sides to agree. The row is directional because a *request* is; friendship itself is symmetric once accepted, so every read looks both ways. B asking A while A→B is already pending is not a duplicate — it is agreement, and `send_friend_request` accepts the existing row rather than creating a mirror. Declining deletes rather than marking, so the requester may ask again; a permanent "declined" row would be a block, which is a different feature. `search_users` is a deliberate, fenced disclosure: ≥3 characters, ≤10 results, matches the email's **local part only** (so `@unipd.it` cannot harvest an institution) and never returns a full address.

**`get_member_profile(p_user)` is the one exception to "no user_id parameter"** — the shape that caused the vulnerability fixed in `20260729210000`. It is safe *only* because its body refuses any target `can_see_user()` rejects. Delete that check and it becomes a full dump of any user by id. It returns another participant's scores, day history **and whitelisted domains** — the last is browsing data and the schema's most sensitive peer-to-peer exposure; it belongs in the consent form. `domain_flags` is a **registry of every known domain** carrying a global red-flag tally, recomputed (never incremented) from the append-only `domain_flag_events` ledger. A row appears with count 0 as soon as anyone whitelists the domain — written by `apply_score_delta` (immediate), swept incrementally by `register_new_domains()` in the `*/5` job (watermark in `maintenance_state`, index on `user_domains.added_at`), and fully by `register_all_domains()` daily at 03:17. The middle one is incremental because at the design scale (50k users ≈ 1M rows) a full `DISTINCT` every 5 minutes is ~17 GB/day of buffer churn for a safety net. Domains are lower-cased on write; `flag_domain` always did, `user_domains` did not, and the mismatch would have made `ArXiv.org` and `arxiv.org` two rows that never join.

**The `*/5` cadence is a correctness property, not a tuning knob** — it bounds how long after a user's local 01:00 their day and flag turn — so the jobs are pruned to fit it. `grant_weekly_flags` finds due users via `flag_week < focus_week(now() + interval '14 hours', 'UTC')`: UTC+14 is the largest real offset, so that is an upper bound no user's week can exceed, and it reads off `user_flags_week_idx`. It is selective because local *weeks* only differ across timezones during the ~26 hours Monday sweeps the globe — empty ~6.9 days out of 7. The same prefilter is deliberately **not** used in `roll_forward_due()`: local *dates* differ continuously, so it would prune nothing; that job stays a scan of the small, cached `user_summary`.

**Red flags are a weekly budget.** `user_flags` holds 0 or 1 per user; `grant_weekly_flags()` (a second `pg_cron` job, same `*/5 * * * *` schedule and same per-timezone reason as the rollover) **sets** it to 1 each Monday 01:00 local — set, not incremented, so an unspent week is lost. Spending is permanent. A **second, independent limit** caps one user at **3 flags on any one domain, ever** — the weekly budget controls how *often* someone flags, the ceiling how far they can push a *single* domain, so a high tally means breadth of objection rather than one person's persistence. The ceiling looks like a check-then-act race but isn't: the single `update user_flags … where flag = 1` serialises a user against themselves, so two concurrent calls can never both reach the insert. Monday 01:00 needs no new definition — `focus_week()` is just `focus_day()` (which already turns at 01:00) truncated to an ISO week, so both turn together. Ranking everywhere is `focus + distracted`, because `distracted_score` is stored *negative* and that expression is "focus minus distraction"; the literal subtraction would rank a distracted user higher. Team totals are **sums** (so `member_count` ships alongside). Per-team lists inside a competition aren't sent separately — each member row carries its `team` and the popup groups by it.
- **The server is the source of truth** for scores, whitelist and history. The extension still writes the same `chrome.storage.local` keys (`focusFlowSettings.allowedDomains`, `focusScoreHistory`), but they are a **cache overwritten by every response**, not a record. It cannot be zero local storage — `heartbeat.ts` must decide whether to activate on every page load, instantly and offline — so everything reading those keys keeps working unchanged. The whitelist is written through `apply_score_delta` (`p_domains`) rather than its own endpoint so an edit and a score delta cannot race; `SERVER_DOMAINS_KEY` records what the server last sent, which is how a server echo is told apart from a real user edit and the write loop is broken.

**Flags cover programs too, through parallel tables rather than a `kind` column.** `user_programs` / `program_flags` / `program_flag_events` mirror the domain trio exactly, with `flag_program()` spending the **same weekly budget** (`user_flags` — one flag a week, spent on whichever of the two you point it at) under its own per-target ceiling of 3. The obvious `kind` column was rejected for one specific reason: `build_state()`'s `domains` array is written straight into `Settings.allowedDomains`, which `heartbeat.ts` substring-matches against every URL, so the day a `where kind = 'domain'` is forgotten, `code` becomes a page-whitelist entry matching vscode.dev, qrcode.com and anything else containing those four letters — silent, absurd, and invisible in the diff. Separate tables make that unrepresentable. `focus_program()` reproduces `normaliseProgram()` from `agent.ts` (trim, lower-case, drop a trailing `.exe`) and everything that writes or looks up a program goes through it; if the two ever disagree, `Code.exe` and `code` become two registry rows that never join. `apply_score_delta` gained `p_programs` and was **dropped and recreated** rather than given a defaulted 5th parameter, because PostgREST resolves an RPC by the set of named arguments it was sent and leaving both signatures would make every existing 4-argument call ambiguous. Note the cross-platform consequence, which is accepted rather than solved: identifiers are per-OS (`code` / `com.microsoft.VSCode` / `code.exe`) while the sync model overwrites the client cache from the server, so a user with two machines of different OSes sees each list replaced by the other's. Foreign entries are inert — they never match locally — and the alternative (union) would make deletion impossible to propagate.

**`push_pairings` is a courier, not a store.** The phone nudge is sent by the user's own browser (see `push.ts`); the only thing the server does is carry one subscription from the phone that scanned the QR to the desktop that showed it. A row lives ten minutes (`pairing_ttl()`), `take_pairing()` **deletes the row it returns**, and after pairing this table knows nothing. `claim_pairing` is **the one function in the schema granted to `anon`**, because the phone is not signed in and never will be: the 128-bit nonce *is* the credential. It is written so that knowing one lets you do exactly one thing — fill in a subscription on a fresh, unclaimed row — and it cannot read a row, list rows, learn a `user_id`, or overwrite an existing claim. It also re-builds the JSON from three extracted fields rather than storing what it was handed, so an unauthenticated caller cannot park arbitrary JSON in the column. `take_pairing`'s `user_id = auth.uid()` is load-bearing for the same reason `get_member_profile`'s visibility check is: the function is DEFINER, so without it any known nonce would hand over that pairing.

**Group charts.** `get_team_days(team)` / `get_friends_days()` return a day series **averaged over the member set**, so the team and friends sections can draw the same two charts the Personal section does. Two averaging conventions, deliberately different: member-level figures (live/7d/30d) count *every* member with a missing row as 0 — matching the leaderboard, so the "7 d" bar equals the mean of the board's 7-day column — while each day's bar averages only the members who **recorded** that day, because a machine that was never switched on is absent, not zero. Fetched **once per section open**, never on the boards' 60-second refresh: a completed day changes once a day. The aggregation helper takes a `uuid[]` and is therefore callable by nobody — `EXECUTE` revoked from everyone, invoked only from inside the two DEFINER wrappers that decide the array themselves.

**The hook point is `updateState()`** in `background.ts` — the single writer of `SessionState`. Diffing `focusScore`/`distractedScore` there means any future code path that awards points is synced automatically. `queueDelta` ignores anything that isn't a *rise* in focus / *fall* in distracted, so the local daily rollover zeroing both counters is correctly not forwarded as a huge negative delta.

**No local day rollover.** `maybeRollover()`/`archiveDay()` are gone on this branch: the server ends the day (cron, 01:00 in the user's timezone) and every reply carries the reset live score plus the 30 most recent completed days, which `applyState()` writes into the local history cache. A second midnight-based rollover could only disagree — the boundaries are an hour apart, so it zeroed the score at 00:00 and had it jump back on the next post. `state.scoreDate` is now set from the server's `live_day`. **Consequence: with no server configured, or signed out, nothing ever ends a day** — the live score grows indefinitely and no history is banked.

**Scores are optimistic locally, authoritative from the server.** A point lands in `SessionState` immediately (so the sprite's `+1` and `−N` fly-up need no round trip), then the post's reply reconciles the displayed figure to the server's live score via `applyServerScores()`. That function goes through `writeState()`, **not** `updateState()` — deliberately: `updateState` would diff the scores it just received and post the difference straight back, compounding on every reply. The reconciled value is `server + still_pending`, because deltas queued mid-flight aren't in the server's figure yet and dropping them would make the number jump twice.

**A focus-day runs 01:00 → 01:00 local**, defined once in the SQL `focus_day()`. Ending a day happens **only** in the `pg_cron` job — it runs inside the database, so it works while the browser is shut, and the extension never triggers a rollover. The schedule is `*/5 * * * *`, not `0 1 * * *`, because a cron time is one wall-clock moment in UTC while users are in every timezone; each pass asks per-user whether *their* day is over. `pg_cron` is therefore **required**, not optional. Note this differs from the *extension's* local midnight rollover, so 00:00–01:00 points land on different days locally vs server-side. Setup and the research/PII caveats are in `supabase/README.md`.

## The Desktop Agent (`desktop/`)

A ~350-line Node program that answers **one** question for the extension: which program is in the foreground. It has **no account, no session, no settings file, no window, no tray and no scoring** — the extension remains the single central node, owning the program whitelist, the heartbeats, the score, the sprite and the sync. Stop the agent and the extension behaves exactly as it did before it existed. Full detail in `desktop/README.md`; the load-bearing decisions are below.

**The extension cannot start it, and no amount of design will change that** — no extension API runs a local program. `chrome.runtime.connectNative` is the only one that can, and its host manifest must name an exact extension ID, which is the same wall that made this a loopback socket in the first place. So starting it is a desktop action: `install-icon.sh` writes a `.desktop` entry (plus a Desktop copy marked `metadata::trusted`, without which GNOME refuses to run it) or a macOS `.app` bundle, both pointing at `launch.sh`. That wrapper exists because a double-click on a windowless program looks like nothing happened: it reports through `notify-send`/`osascript`, refuses to start a second copy, finds a node that a desktop launcher's PATH would miss (nvm, Homebrew), and builds `dist/` on first click. `launch.sh stop` reads the agent's **own pid from its HTTP reply** rather than matching a command line — `npm start`, the icon and a hand-typed `node dist/index.js` produce three different command lines for one agent, and a `pkill -f` pattern loose enough to catch all three catches other things too (it will happily kill the shell that ran it).

**It exists to name `osHeld`.** `chrome.idle` can only say "input happened somewhere", which is why the violet countdown exists at all. The agent attaches a program name to "somewhere", so the extension can tell a local LaTeX editor apart from a game — the one judgement `chrome.idle` structurally cannot make.

**Transport is HTTP on loopback, polled — not native messaging.** `chrome.runtime.connectNative` would be canonical, but a native-messaging host manifest must name the exact extension ID it may talk to, and this extension's ID is not pinned (it changes when the unpacked folder moves). A loopback port needs no manifest, no ID and no installer writing into the browser's configuration. The extension already polls `chrome.idle` at 2 Hz; `src/extension/agent.ts` rides along with that poll, throttled to 500 ms while the agent answers and backing off to 15 s while it does not.

**Three independent reasons a web page cannot read it**: the socket binds to `127.0.0.1`; **no CORS headers are sent**, so a page's `fetch` is blocked from reading the response by the browser itself while the extension is exempt through its `host_permissions` entry; and any request carrying a web `Origin` is refused with 403. The port `47317` appears in exactly three places — `manifest.json`, `src/extension/agent.ts`, `desktop/src/index.ts` — so changing it means changing all three.

**The decision table lives in `heartbeats.ts`, not in the agent.** Folded into `pollOsIdle`:

| `chrome.idle` | Foreground program | Result |
|---|---|---|
| idle | anything | idle |
| active | on `Settings.allowedPrograms` | **working** — counts with no tab involved, `osHeld` true |
| active | a **browser** | the active tab decides, exactly as before |
| active | anything else | **not counted** — the session expires to idle |
| active | agent absent | the active tab decides, exactly as before |

**Browsers are excluded and cannot be whitelisted.** The agent only knows "Chrome is in front", which says nothing about Overleaf versus Instagram; the extension already knows, and the page whitelist is where that judgement belongs. Treating a browser as work would count every distraction site as work; treating it as not-work would discount everything the extension exists to measure. Hence the third row above, which is not an optimisation but the whole reason the fallback path is preserved verbatim.

**`allowedPrograms` is a separate list from `allowedDomains`**, not a variant: a domain is matched by substring against a URL, a program by an **exact** platform identifier (executable name on Windows, bundle id on macOS, `/proc/<pid>/comm` — 15-char capped — on Linux). Exact matching is deliberate: a rule for `code` must not silently claim `vscodium`. Default empty, because there is no useful cross-platform default; the popup offers the program you are using right now with one click, which is far better than asking someone to recall `gnome-terminal-`.

**The identifier is the key; the name is only a label.** Every UI shows the human name with the identifier in fine print, because a list reading `code`, `winword`, `com.apple.preview` is unreadable — those are matching keys, not names. `agent.ts` learns id → name from each reading (`AgentStatus.names`), but writes to disk (`focusProgramNames`) **only the ids that are on the whitelist** — `background.ts` declares which through `setNamedPrograms()` on every settings change, since the module must not read `Settings` itself. Names for anything else stay in memory and die with the worker: a persisted list of every application that has ever been in front of you is a record of the user's day, and the only names worth displaying are the ones on a list they wrote themselves.

**One long-lived helper process per platform**, never one per sample, each printing the same `id|name` line so a single parser serves all four sources. **No window title is ever reported** — they leak document names, message contents and page titles. The one exception looks but never tells: the Windows helper compares titles with the constant `PIN_TITLE` to find the companion window (below), discarding them immediately. macOS uses `lsappinfo` rather than System Events precisely so no Accessibility/Automation permission is ever requested. Nothing is written to disk.

**Pinning the companion window is three answers, not one feature.** A browser cannot raise its own window on Wayland, so something outside it must — and what that something is differs completely by platform. **GNOME:** the Shell bridge, `make_above()` from inside the compositor. **Windows:** this agent, `SetWindowPos(HWND_TOPMOST)` from the same PowerShell helper — the only place the agent does something other than sense, justified because Windows has no built-in always-on-top and no compositor extension point; one program may raise another's window there, needing no elevation and no injection. **macOS:** nobody. No public API lets a process change another application's window level, which is why every utility that does it is an Accessibility-granted window manager; the README lists them. Both implementations use the same two guards — the title must start with `Focus companion` (`pip.html`'s `<title>`, `COMPANION_TITLE`, `PIN_TITLE`: three copies of one string) and the window must be under 900×700, so a page carrying that title cannot drag a browser window on top and a stretched companion never becomes an overlay you cannot work under. Windows additionally skips a window that is already topmost, so unpinning by hand sticks.

**The GNOME bridge pins, places AND fades the companion window**, because it is the only code in the project that runs *inside* the compositor. Those are exactly the three facts about its own window that a Wayland client is not allowed to decide, which is why all three ended up here rather than beside everything else the window owns.

**Translucency is the third, and it cannot be done in `pip.html`.** `chrome.windows.create` opens a real toplevel that the browser paints onto an opaque surface, so `background: transparent` falls straight through to the browser's base colour; the one API that could (Chrome Apps' `transparentBackground`) went away with Chrome Apps, and a document-PiP window is opaque too. The opacity is set on the window **actor** — the handle on how a window is *composited* rather than where it sits. Note what that does and does not buy: Clutter applies the alpha to the whole actor, so this is **uniform translucency, not a transparent background behind opaque content** — the character and the score fade by exactly as much as the panel under them. That is the honest cost of doing it from outside the window, and it is why the useful range sits high: the companion exists to be caught out of the corner of your eye, and one dimmed far enough to read what is behind it is one you stop noticing — which would spend the legibility the tremble and the countdown are built on. It is also **not** click-through; seeing what is underneath and being able to click it are separate features. **It is the one thing here that is a real preference and therefore the one thing with a settings UI** (`prefs.js`, a `companion-opacity` GSetting, default 180 ≈70%, floor 40 so nobody can slide an invisible window into being): the right value depends on the wallpaper behind it, so it can only be found by looking — and because the Shell loads extension code only at start-up, every experiment with a constant cost a whole logout. The extension watches `changed::companion-opacity` and re-fades every window in `_placed` (already exactly the set of recognised companions, already emptied on `unmanaged`, so the two cannot disagree), and `disable()` restores 255 — a disabled extension that left every companion faded would read as a bug whose explanation lives in a dialog belonging to the thing just switched off.

**Windows gets the same feature and macOS still gets nothing**, so this is the pinning story's three answers a second time. `SetLayeredWindowAttributes` sits beside the agent's existing `SetWindowPos` in the one PowerShell helper, in the same 0–255 unit, so one number describes the window on either platform. Two differences from the pin, both deliberate: the fade is re-applied on **every** pass while the pin is one-shot (a window un-pinned by hand must not be fought over twice a second, but re-applying the alpha is what lets a restarted agent update companions that are already open), and it is configured by the **environment variable** `FOCUS_COMPANION_OPACITY` rather than a file, because the agent has no settings file and must not grow one — every other configuration decision in this project belongs to the extension, or on GNOME to the piece that has a preferences dialog. 255 disables it and the layered style is never set.

 Placement is the same wall as pinning: `chrome.windows.create({left, top})` is honoured on Windows, macOS and X11 and ignored on Wayland, so `_place()` puts each companion bottom-right of the first monitor that has not got one, using the **work area** rather than the monitor rectangle (the difference between "bottom-right" and "underneath the dock"). It runs **once per window**, on the frame it is recognised — re-placing on every title change would drag a companion the user had deliberately moved back into the corner, and that is a fight the user has to win. The monitor→window map is cleaned on `unmanaged`, so closing a companion frees its screen for the next one. On Wayland a client cannot raise its own window — the fact that deleted the picture-in-picture overlay and left "pin it with your WM" in the README — but `Meta.Window.make_above()` is one call from a Shell extension. It matches `pip.html`'s exact `<title>` (`COMPANION_TITLE`, so the two are coupled) and refuses anything larger than 900×700: a page that happens to share that title must not drag a whole browser window on top, and an always-on-top window big enough to cover the work is exactly the failure that got the Electron overlay deleted. It is watched via `window-created` **plus `notify::title`**, because a browser window is mapped before its title is set — checking only at creation examines it while still `about:blank` and never looks again. This is the one place anything here reads a window title, and it compares it with a constant rather than reporting it.

**Wayland takes a per-compositor path, and GNOME's is built.** A Wayland client cannot see other applications' windows by design — under Xwayland `xprop -root _NET_ACTIVE_WINDOW` answers `0x0` forever — so the only way through is to ask something already *inside* the compositor. `desktop/gnome-extension/` is a GNOME Shell extension exporting one D-Bus object (`dev.focus.Companion` at `/dev/focus/Companion`), needed because `org.gnome.Shell.Eval` has been locked down since GNOME 41. **It emits the same line the X11 helper prints**, so identifiers and the whitelist are identical on either session type. Installing needs a **log out and back in**, and there is no way around it: `ReloadExtension` answers "deprecated and does not work", `EnableExtension` returns `false` for an extension the Shell has not scanned, and `Introspect` is `AccessDenied` outside a fixed allowlist — the Shell scans that directory only at start-up. `install.sh` therefore writes the `enabled-extensions` GSetting itself rather than telling the user to run `gnome-extensions enable`, which cannot work before the logout. KDE (a KWin script) and wlroots (`swaymsg`/`hyprctl`) are the same shape and deliberately not implemented; those sessions report no program and the extension falls back to browser-only tracking.
